## 1. 已确定的产品方向

Task 是用户交付给系统的一件工作，不是一次聊天，也不是必须走完的固定流水线。用户描述目标后，系统在约定范围内自主理解、执行、检查、修复，并按授权完成提交或部署；只有存在真实阻塞、预算不足或必须由用户决定的事情时才请求介入。

Pi SDK 是主要执行引擎，优先为其优化。ACP 长期保留，继续支持 mfcli 等外部 Agent；统一 Task 和 UI 不要求内部执行能力完全对称。移除 ACP 不是本方案目标，也不是 Task 的前置条件。

Workspace 在产品上弱化为执行环境，默认使用项目当前工作目录。保留现有 worktree 能力，在需要隔离时使用，而不是每个任务必建分支。Terminal Agent 降低新功能投入，但 Shell、测试进程、服务、日志和取消能力仍是核心基础设施。

### 1.1 两项核心及其关系

**标准是完成约束，速度是优化目标。**

完成标准定义什么才算做完、需要什么检查依据、允许交付到哪里。执行策略选择达到标准的最小充分路径。不能通过删除必要检查来提速，也不能通过增加无意义阶段来制造严谨的外观。

速度衡量从下发到真实交付的总耗时，包括返工和人工接力；不是首字延迟或第一次宣布完成的时间。

### 1.2 明确不做

第一版不做通用 DAG 工作流平台、不固定配置规划/开发/测试/评审四个 Agent、不在每次工具调用后增加监督模型、不重写 Pi Agent Loop、不全面更名或重写 ACP 会话协议、不新建第二套 Host 数据权威、不强制每任务 worktree、不让所有普通对话都必须创建 Task。

暂不扩大手机端、分布式执行、插件市场或长期记忆平台。没有真实性能测量，不声称绕过 ACP 会明显更快。

## 3. 用户入口与日常体验

保留两个入口：**对话**和**执行任务**。对话用于咨询、讨论、临时探索；执行任务表示系统将持续推进到约定终点。对话可转为 Task，保留来源 Session、选定结论和消息范围，不要求重新描述问题。

新建任务默认只需项目和目标。继承项目默认 Agent、执行策略、交付终点与预算，输入区紧凑展示：`Pi · 自动 · 当前目录 · 修改并验证`。这些配置可以展开修改，不作为必填表单阻挡小任务。

### 3.1 轻量任务

“把按钮文案改成开始执行”：定位、修改、检查引用或语言项、展示结果。不要额外分类调用、单独计划调用、独立评审调用、总结调用或全量测试；Task 元数据记录不应要求额外模型轮次。

### 3.2 普通需求/缺陷

“修复流式输出截断”：同一个 Pi 定位与复现、修改、执行相关检查；失败时依据真实错误继续修复。复现复杂性增加时只补充必要诊断，不重新启动整套流程。

### 3.3 带交付任务

“完成某个功能，验证后部署测试环境”：先执行与验收，再对经过验证的代码/产物发布并检查目标环境。不因为选择了深入策略，就自动获得推送、生产部署或数据迁移授权。

### 3.4 运行中交互

用户可以追加指导、改目标、缩小交付范围、暂停、取消。追加指导优先继续当前执行上下文；正式目标或交付策略变更必须写入 Task 修订记录，而不能只存在聊天文本中。

“先别部署”之类明确限制立即更新控制状态，发布前再次检查。已发出的外部操作不保证能撤回，要反馈实际状态。歧义较大时先冻结相关高影响动作，再一次性询问必要信息。

## 4. 核心领域模型

### 4.1 Task：长期目标

保存 `id/projectId/title/goal/constraints/contractRevision/acceptance/strategyPreference/deliveryPolicy/source/currentRunId/desiredState` 等。来源可为用户、聊天、Issue、Todo、Automation。

Task 保存目标与决策，不复制全部聊天。一个 Task 同时只能有一个主活动 Run。任务完成后的新请求可以开启新 Run；无关目标应新建 Task。

### 4.2 TaskRun：一次持续执行尝试

保存本次契约快照、实际 Agent/model、策略、执行环境、主会话及子会话引用、阶段、预算、检查和交付操作引用、结果、恢复游标。

自动修复属于同一个 Run 内的迭代，不为每次模型响应或失败检查创建新 Run。人工重试终态任务创建新 Run，旧结果不覆盖。

换 Session 不等于换 Run。默认一个主 Session 持续执行；上下文质量不足、会话不可恢复或需要独立复核时才新建，并带上精简交接。

### 4.3 Session：执行上下文

继续使用既有会话和日志设施，TaskRun 关联 Session，而非重建聊天数据库。活动 Session 不同时归属于两个独立主 Run；关联历史或聊天转任务不等于复制执行。任务控制命令归 Task Runner 单一入口，避免普通聊天队列和 Task 队列争相提交。

### 4.4 Evidence：检查与交付依据

记录真实工具/进程/测试/浏览器观察，而不是只保存模型的“通过”描述。每份证据明确其范围、版本和来源。语义评审可以是证据的一种，但与运行事实分开标记。

## 5. 完成契约：标准从哪里来

任务契约由项目默认要求、用户本次要求、实际影响范围共同形成，至少表达目标、范围、不做什么、完成条件和交付终点。

小任务可以直接使用用户原文加项目规则，不先生成长文档。Pi 首次正常分析时可提炼条件，不增加专门的“契约生成 Agent”。结构化提炼不得重新解释或降低用户已明确要求；尚有影响结果的歧义时不能发布。

每个验收项建议包含：`id/description/origin/required/evidenceKind/checkRef`。来源为用户、项目配置或 Agent 补充。所有本次适用的 required 项都必须满足；not_run、unknown、stale 不等于 passed。

项目固定检查不是完整验收。例如类型检查成功不能证明交互 Bug 修好。针对功能目标需要对应观察、断言或适当的人工验收；纯主观审美无法客观证明时，不把模型自评分当成无条件成功。

### 5.1 契约和策略分开修改

Runner 可加强执行和补充合理检查，但不能通过去掉失败条件、降低断言或扩大交付权限推进。用户改变目标或允许例外时增加 `contractRevision`，保留变更原因。

Run 固定使用生效的契约/配置快照。旧版本候选结果和迟到事件不能让新版本任务变成成功。明确免除某项检查必须显示为“用户接受例外”，不能伪造通过。

## 6. 自适应执行策略

只做一个 Runner。直接、标准、深入是策略预设，不是三套执行引擎。默认自动，用户可固定偏好；固定快速偏好也不覆盖必要标准和交付限制。

| 维度 | 直接执行 | 标准执行 | 深入执行 |
| --- | --- | --- | --- |
| 适用 | 明确、局部、低风险 | 一般功能和缺陷 | 高不确定性、跨模块、高影响 |
| 规划 | 无独立规划步骤 | 必要时简短计划 | 阶段化目标与风险处理 |
| 上下文 | 相关文件和关键约定 | 相关调用链 | 依赖、运行环境、历史决策 |
| Agent | 单个主 Session | 单个主 Session 为主 | 按需委派/独立复核 |
| 验证 | 最小充分检查 | 定向测试及必要运行检查 | 集成、原始场景和高风险检查 |
| 失败 | 当前 Session 修复 | 错误证据驱动修复 | 定位、调整计划或阻塞 |
| 禁止 | 以快为由省略必要检查 | 固定全量测试 | 固定多 Agent 和无界循环 |

初始选择使用用户明确要求、项目规则、影响和风险信号；不额外调用模型分类。不能仅按字数、文件数、改动行数判断，小型鉴权或发布配置修改也可能高风险。

执行中同一个 Pi 可以报告影响扩大，Runner 按规则增加检查或预算内投入。不因一次测试失败自动升级；出现重复失败无进展、范围明显扩大、无法复现等信号时再调整。策略加强不必新 Session；问题被证明简单后可移除无意义阶段，但保留 required 条件。

### 6.1 预算与优先级

独立配置执行时限、修复上限、重复无进展上限、并行上限和可获得的费用预算。金额不可靠时标为估算或未知，用可观测时间/次数补充控制，不能承诺精确硬截断账单。

预算耗尽保留结果并报告未完成项，不通过降低标准“成功”。实际执行默认尊重用户选择的模型和提供商；不得悄悄换便宜模型或把公司代码转交另一模型端点。

小任务可在不同项目可用执行槽中优先开始；同一目录有活动写入任务时仍需协调。不得为抢占小任务，在任意工具执行中强行中断当前任务。展示队列等待原因，并允许明确调整优先级或改用隔离环境。

## 7. 目标架构与第一阶段落地

### 7.1 逻辑架构

```text
用户 / 对话转任务 / Todo / Automation
                    |
                    v
       Task Service + Task Runner（Host）
       目标、策略、预算、验收、恢复、交付
                    |
            Task Execution 接口
           /                   \
          v                     v
  Pi 专用 Driver            ACP Driver
  原生 SDK 能力             mfcli 等外部 Agent
           \                   /
            统一任务事件与结果
                    |
       现有 Timeline / Task 视图

执行环境、Git、进程、验证、发布：复用 Host 能力
```

Task Execution 是小型接口，不是第二个 ACP 标准。不把所有厂商抽象成庞大 Provider 框架。目标与结果通用，Pi 特有控制按能力显式提供。

### 7.2 第一阶段真实进程路径

```text
Host Task Runner
    -> PiTaskDriver
    -> 现有 AcpSessionRuntime / acp-daemon
    -> Pi SDK Adapter 子进程（必要的原生事件扩展）
    -> Pi SDK

Host Task Runner
    -> AcpTaskDriver
    -> 同一现有会话基础设施
    -> mfcli 等外部 ACP Agent
```

两条逻辑 Driver 初期可以共享现有传输，不要求先新增进程或改写 UI 协议。Pi Driver 的区别是了解原生生命周期、工具记录和能力，不只是换一个 harness 名称。

Task 新入口必须显式传入已选择的 harness 和模型；当前会话 API 的说明是省略 harness 仍保留 Claude 默认行为，不能因为产品称为 Pi-first 就假设底层自动选择 Pi。任务入口默认 Pi，但不全局改写旧会话或用户已有设置。模型要求明确时使用现有 strictModel 能力或等价的实际模型核对，无法满足时提示，不能静默忽略。[S3][S15]

后续只有出现明确的能力阻碍、可测性能瓶颈或维护收益，才把 `pi-sdk-acp.ts` 拆为 Pi 执行核心与 ACP 编解码。拆分时保留单一事件源，再生成兼容 UI 投影；不能同时启用两条重复事件路径。ACP 支持长期存在，Pi 传输也不承诺最终删除。

保留 Pi 独立进程，不把 SDK 塞进 Electron 主进程。Host 仍是 Task 业务权威，Renderer 只渲染。新增内部事件须做版本兼容与能力协商，不让旧客户端因新枚举而崩溃。

## 8. Pi 深度接入及控制归属

本地安装 Pi SDK 为 0.84.2。其声明包含 `agent_settled`、队列、压缩、自动重试事件，以及自定义工具；当前适配把部分压缩事件转为普通聊天文本。[S2][S12]

### 8.1 必要的原生信号

按需求映射为 `execution_started / runtime_busy / execution_settled / execution_failed / execution_cancelled / intervention_required / check_recorded` 等内部事件。

`agent_end`、SDK promise 返回或 ACP end_turn 不能单独作为业务成功。Pi 的 settled 信号也只说明原生循环已收敛，仍需检查 Host 队列、未完成验证、子任务和本次 Run 所拥有的进程。长期保留的开发服务必须显式登记为保留资源，不无限等待，也不静默遗留。

实现前针对已安装版本验证顺序与异常路径，不根据上游 main 的文档假定本地行为相同。

### 8.2 单一控制入口

Task Runner 持久化控制意图与外层待执行命令；Pi 管模型调用、工具循环、原生压缩和请求重试。外层只管任务修复，不重复启动请求级自动重试。

第一版继续复用现有 Host follow-up queue，不再同时开启 Pi 原生 followUp 作为第二份独立队列。steer 可由当前适配落到 SDK；任务级 commandId 持久化去重。以后替换队列实现时一次只切换一个权威。

不能按“长时间没输出”直接重发原始任务。先判断是否正在工具调用、压缩、重试、等待输入或已失联；重连应先对账。

### 8.3 工具接入

保留 Pi 常用文件与 Shell 能力，增加少量任务功能，例如读取目标、记录检查、提交候选结果、报告阻塞。名称为接口设计，不是当前已存在的工具。

可观测性优先在真实工具/进程执行边界记录，不让模型填一个 `passed` 就成为证据。自定义工具注册、Shell 包装需保持取消信号、流式输出、工作目录和错误语义。SDK 事件没有包含退出码等必要信息时，需要执行器补充，不能凭 `tool_execution_end` 直接推断测试通过。

普通 Shell 保持可用；最终验收检查优先通过 Host Check Runner 或有完整记录的工具路径。无法观察的外部执行可以展示 Agent 上报，但不冒充运行时验证。

### 8.4 候选完成不要增加固定模型轮次

候选结果可复用同次执行的最后输出或工具结果，由适配器记录候选边界；不要为了填一份结果表再调用一次模型。结构化上报用于引用实际证据，不由模型修改任务状态。

小任务已有足够的确定性证据时，Gate 直接判定；确实缺少语义信息才继续一次有目的的评估。单独总结不在默认关键路径中。

## 9. ACP 兼容策略

mfcli 继续使用现有认证与公司额度路径，不提取凭据转交 Pi，也不假设两者模型上下文可无损共享。

Driver 显式声明能力及来源，例如追加指导、持久恢复、实际停止确认、工具可观测性和用量记录。未知能力不标为支持，旧版本不凭名称猜测。

缺少 Pi 专有事件时用 ACP prompt 终态、工具状态和能力检测完成执行对账；不要用终端文本关键词伪造强状态。若 mfcli 无法提供足够检查依据，可由 Host 独立执行项目检查。缺少必需验证能力就阻塞或标明待验收，不降低标准。

UI 的暂停/取消必须有统一含义，底层达不到时显示能力限制。例如未确认进程停止，不能展示“已全部停止”。不能保持表面按钮统一而谎报状态。

Agent 切换由用户选择或项目显式策略控制。切换需创建新执行上下文，带目标、当前版本和检查证据；不在原 Session 内假装无损换引擎。涉及不同提供商的数据流转也必须符合已有授权。

## 10. Task Runner 状态、循环与完成判定

### 10.1 状态和阶段分离

建议 Run 状态：`queued / running / pausing / paused / blocked / cancelling / recovering / succeeded / failed / cancelled`。

阶段独立表示：`understanding / implementing / verifying / delivering`。小任务无需经过所有阶段。`failed` 用于无法继续的终态；等待可补齐信息用 `blocked`；不确定旧执行状态用 `recovering`，不能误标取消或失败后马上复制执行。

Task 展示状态从主 Run 和用户意图得出，不让前端和后端分别维护一套会分叉的状态机。

### 10.2 事件驱动协调

```text
持久化 Task 与 Run、契约、commandId
    -> 获得执行协调权与环境
    -> 提交一次 Pi/ACP 执行
    -> 订阅并保存控制事件、检查记录
    -> 等待执行收敛和候选结果
    -> 验收
       -> 满足：按交付策略推进或完成
       -> 可修复：把具体失败交回当前 Session
       -> 缺条件：blocked
       -> 预算耗尽/不可恢复：failed，保留已有结果
```

常规工具循环由 Pi 完成，Runner 不逐工具调用监督模型。真正持久化的是执行事实、检查和关键状态，而不是重新复制每个文本 token。

### 10.3 完成判定条件

只有同时满足以下条件才成功：候选结果属于当前 Run 和契约修订；无未处理的任务内指令；执行、必要子任务与验收步骤已结束；所有适用 required 条件有有效依据；证据覆盖当前代码/环境；交付终点已达到；未被取消或撤回授权。

`accepted`、`idle`、`end_turn`、`tool_success`、`agent_settled` 和“我已完成”都不是单独的成功条件。候选上报后继续修改代码，必须使受影响证据失效并重新检查。

主 Run 终态通过事务和版本比较提交。取消与成功竞态按已持久化的控制意图与状态版本解决；已成功的结果不能被迟到失败事件覆盖，新 Run 也不能被旧事件改写。

## 11. 验证与证据：最小充分，而非固定全量

### 11.1 项目执行配置

新增版本化 Task Profile，第一版保存在 Host 项目设置中。可复用现有脚本信息进行建议，但自动发现不等于已批准的发布配置。[S11]

配置包括项目约定、检查目录、检查适用范围、超时/资源、交付默认值和已授权环境。没有 Profile 时仍允许普通 Task；针对任务选择检查。不能因为缺少配置就伪造全量验证完成。

后续需要共享配置时增加明确的导入/导出和版本规则，不同时让 Host 配置与仓库文件各自变成权威。当前 `.superset/config.json` 的 setup/run/teardown 行为继续兼容。

### 11.2 检查分类

检查集合包括静态、单元、集成、真实运行、浏览器场景、代码变更审核和部署健康检查，但按影响选用。某些检查可不适用，不必每次运行全套。

针对 Bug 优先保留原始复现，能安全重复时记录修复前失败和修复后通过。无法稳定复现就明确验证限制，不能拿一个不相干的模拟场景代替。对于明确要求真实验证的任务，只有单测通过不足以完成。

已有仓库失败要记录基线和本次影响，不能把全量红灯包装成全量通过，也不要为了无关旧错误无限扩大任务。由本次契约决定是否允许已知基线例外。

### 11.3 Evidence 字段

建议记录 `checkId/runId/contractRevision/source/toolCallId/processId/argv/cwd/start/end/exitCode/result/artifactRefs/inputFingerprint/checkConfigRevision/environmentFingerprint`。

状态包括 `passed / failed / not_run / unknown / stale`，单独保存原因和是否适用。执行命令最好保存 argv 和实际 Shell 语义，不能靠展示用的命令字符串还原执行结果。

区分运行时观察、Agent 上报、模型评审、人工接受；测试退出码证明的是该检查结果，不是需求全覆盖。模型生成的测试也可能遗漏条件，故检查内容、覆盖范围和对测试配置的改动必须可见。

### 11.4 证据复用与失效

有效性至少依赖被检查源码、相关测试/配置、依赖锁文件及环境。对未提交代码，HEAD 不足以标识输入；应记录工作目录输入指纹。

第一版仅在当前 Run 中做保守复用，不建设跨项目测试缓存平台。使用版本代次和关键边界输入快照，不每个 token 或工具调用后哈希全仓库。不知道影响范围或观察到外部变化时宁可扩大失效范围。

Pi 已经执行过、记录完整、输入仍适用的检查可以直接采纳。修改相关代码或检查本身后失效；不因为想省时间保留过期绿灯。构建输出和日志等生成物应与输入分开，避免把检查本身产生的文件误判为所有证据失效。

发布前需要更强的一致性：验证和发布绑定同一不可变产物/代码快照。共享工作目录中的最佳努力观察不能承诺证明任意并发修改下的完整正确性。

## 12. 同目录多窗口与执行环境

### 12.1 默认行为

普通聊天和手工多窗口保持可用。托管 Task 默认当前目录，不强制创建 worktree。

第一版同一规范化实际目录内只安排一个托管写入 Run；其他托管写入排队，不对所有手工编辑器加全局禁用。不同目录/项目可在资源预算内并行。只读分析可以并行，但测试、构建会写缓存/数据库或占端口，不能简单归为只读。

并行需求明确时才使用独立工作区及独立临时分支，不能假设同一分支可以无条件在两个 worktree 同时检出。隔离后的合入、冲突处理和合入后重验都算任务成本。

### 12.2 已有修改和归属

开始记录工作目录、当前分支/HEAD、已有 staged/unstaged/untracked 改动边界。本来就脏的工作区并不禁止修改，但提交和发布要求能够确定归属。

不要自动 reset、清理、stash 用户修改；不要 `git add .` 把别人的工作一起提交。同一文件混合编辑无法可靠归属时，停止自动提交，展示冲突或请求用户确定；不能凭文件名认为整文件属于本 Task。

工作区分支被外部切换、输入被其他窗口修改时，重新检查基线和受影响证据。隔离任务不能默默只从 HEAD 开始而遗漏用户要求依赖的未提交代码；需要显式选择并记录输入快照。

### 12.3 锁和子任务

按规范化路径协调，Git 引用等跨 worktree 操作另按实际仓库资源协调。已有 provisioning 租约可参考事务模式，但不直接拿来覆盖整个 Task。[S10]

锁是内部协调，不是文件系统安全沙箱。外部 IDE、Shell 和未接管的 Session 仍可修改；无法确认一致性时阻塞提交/发布或改用隔离环境。

父 Run 持有写入协调权时，子任务按根 Run 归组，写入子任务串行推进，父任务不同时写；不能让父任务持锁等待同锁子任务形成死锁。真正并行修改使用隔离目录。

## 13. 持久化、恢复、暂停与取消

### 13.1 最小持久化

第一版建议在现有 `host.db` 中新增 `tasks / task_runs / task_checks / task_events` 四组数据；不另建数据库。

Task 保存版本化契约和控制意图，Run 保存快照、会话关联、执行预算、恢复游标与结果，Checks 保存可查询检查记录，Events 保存少量控制动作、状态变化、策略调整、命令意图与确认。

会话、文本流和工具明细继续引用现有 session journal/transcript。日志、截图和产物放 Host 管理的工件目录，DB 只保存索引和哈希。需要多 Session 时先使用有界关联记录或既有 delegation 表，不预建复杂 DAG 表。

后续正式交付阶段新增可查询的 `task_operations`，记录提交、推送、部署的 intent/submitted/confirmed/failed/unknown。不承诺完整事件溯源重放，不为简单事务引入消息中间件。

### 13.2 恢复与去重

先持久化 Run 和 commandId，再发执行命令。Host 重启先查询 daemon 是否仍在执行，再恢复订阅和游标，不直接重新发原始需求。事件保留来源 epoch/seq；无法回放时请求状态快照和对账，不能默默认为丢失事件是成功。

单主 Runner 使用状态版本与所有权代次避免重复驱动；租约过期不等于旧进程已死。不能只因超时就把目录写入权交给新任务，先确认旧执行或隔离它。关键副作用操作在执行器入口检查有效代次；任意外部进程不承诺可强制 fencing。

本地命令去重不能保证外部副作用 exactly-once。提交、推送、部署响应丢失时先查提交 ID、远端状态或发布记录；结果未知保持 unknown/blocked，不盲目重跑。

### 13.3 暂停与取消

暂停立即持久化 desiredState 并阻止下一步派发；当前工具可在安全边界结束或通过驱动中断。暂停后保存进展，恢复不是重做已经确认完成的发布操作。没达到停止边界时展示 pausing，而不是立刻显示 paused。

取消覆盖当前执行、子任务、队列、Task 所拥有的验证进程和待交付动作。`cancel` 发出不等于进程已终止。保留 cancelling，等待确认；无法确认的远程进程和部署要单独反馈。保留已修改文件和证据，取消不默认回滚代码、不删除历史。

取消后禁止自动修复重新启动它。强制结束只能针对本 Task 确认拥有的进程，不能杀同机器其他项目进程。暂停释放写入协调权之前也必须确认不存在仍在写入的任务进程。

### 13.4 应用生命周期

Task 视图关闭仅 detach，不能调用现有永久 close；删除历史是另一动作。现有普通 Session 的关闭行为不全局改变。[S8]

第一版 Runner 位于 Embedded Host：页面关闭、路由切换不影响任务；Desktop 完全退出后不承诺完整自主推进。部分 daemon 执行可能继续，但必须在重开后对账。正常退出时提示活动任务，协调暂停；崩溃则按恢复流程处理。

需要退出应用后持续工作的阶段，可将同一 Host/Runner 交由独立服务管理；保留一个数据权威，不复制第二套后台执行系统。休眠、断电、失网与关闭页面分开说明，不承诺应用能在睡眠机器上持续运行。

## 14. 提交与部署

执行策略、交付终点和授权是独立维度。项目可允许修改、验证、提交、推送、发布指定环境；不设计繁琐的多级审批，每次普通读写不要求确认。高影响操作依据明确项目/本次授权执行。

第一版默认修改并验证。正式交付阶段使用显式项目发布配置，不由 Agent 自己发明生产地址、凭据、数据库迁移命令或回滚方式。

```text
锁定通过验证的输入/产物
  -> 核对修改归属与目标分支
  -> 在授权范围内 commit / push / publish
  -> 记录实际发布 ID 和产物 ID
  -> 检查发布版本、健康和关键场景
  -> 达到交付终点，或失败/阻塞并报告
```

GitHub PR 不是唯一方式，也支持项目已明确授权的目标分支推送；不能把直接推 main 当所有项目默认值。只提交本 Task 可确认归属的改动。

若已有项目 CI/CD，就对接它的触发与状态，不再重复建设第二套部署平台。没有可查询状态时不能保证网络中断后自动判断结果。

生产发布、数据迁移、不可逆数据操作分别配置。回滚只有在项目提供明确可用方法且授权时自动执行；代码回滚不等于数据库数据可回滚。

严格的发布权限必须在真正执行边界生效。若任意 Shell 同时拿到生产凭据，UI 上“禁止部署”只能是软约定，不能声称硬隔离。要求强约束时把发布凭据只提供给发布执行器；该选择不要求普通开发命令全部加白名单。

## 15. 上下文、记忆与会话切换

复用现有项目记忆、技能和 ResourceLoader。先提供任务目标、必要约定、相关记忆索引、当前版本及检查结果，按需读取详情，不每次注入全部历史或整仓库。

不绕过必要的项目/用户指令来节约 token。对资源清单和稳定配置可以缓存并按版本失效，不能重复读取后再假装节约上下文。

Task 状态不是 Project Memory。跨 Session 交接带目标与限制、已确认事实及来源、修改摘要、检查状态、未完成项和失败方法；不复制全部聊天，也不把“模型认为的结论”变成未经核实的项目事实。

只有稳定、可复用、有来源的结论才考虑沉淀项目记忆；不自动把每次猜测、临时 workaround 和敏感日志永久写入。

## 16. UI 与信息组织

### 16.1 导航

新增自主 Task 中心；现有 PR/Issue 功能保留，可在导航上改为代码协作入口。第一版用新路由避免破坏现有 `/tasks` 深链，正式调整导航时再保留兼容跳转。

Todo 继续表示提醒/待办，Automation 表示何时创建任务；不要把它们强行塞进同一个表。需要执行的 Todo 或新 Automation 运行关联 Task。历史 dispatched 记录不能批量迁移成 succeeded，旧记录显示未跟踪验收。

### 16.2 Task 列表

优先显示任务标题、项目、当前动作、运行状态、需要用户处理的原因。可过滤进行中、待处理、失败、完成；不以几十个 Session 为首页信息中心。

不使用无法计算的“完成 80%”。知道检查总数时显示已完成检查数，显示“正在复测原场景”比伪造进度更有用。

### 16.3 Task 详情

顶部显示目标、运行阶段、当前策略及调整原因、交付终点。下方提供结果/变更/检查/执行记录，直接嵌入现有统一 Timeline，子会话默认折叠。

用户首先看到做了什么、还差什么、为什么没结束；需要时再看模型输出和日志。完成摘要复用同次执行结果与结构化检查，不为了生成漂亮报告固定追加模型调用。

关闭视图与停止分开，错误/阻塞通知附带继续入口。正常运行不频繁弹通知；真正需要决定的事情集中一次问清楚。mfcli 不支持的能力标明而不隐藏事实。

API 最小集合：创建/启动、查询/订阅、追加指导、修改契约、暂停/恢复、取消、重试、读取检查。内部 Driver 提供 prepare/submit/inspect/subscribe/interrupt 与能力信息；提交回执与完成事件分离。追加指导不支持时返回能力限制或排队，不假装已立即生效。

## 18. 分阶段实施与每阶段交付标准

### 阶段 A：轻量闭环和必要可靠性

交付 Task/Run、单 Pi 主执行、直接/标准策略、小型 Driver、候选与检查记录、一次受控修复循环及可配置预算、任务视图、停止/恢复/页面 detach、同目录托管写入协调。

同一批完成关键故障路径，不能把取消、重复启动和外部改动问题全部推迟到“可靠性阶段”。旧 Pi/mfcli 普通 Session 照常可用，ACP 通道不删除。

验收：小改动没有固定分类/规划/评审/总结模型调用；普通 Bug 首次检查失败后自动修复；缺少必要证据不显示完成；关页面不停止；重连不重复启动；取消不会自动复活；不会提交原有他人修改。此阶段不声称支持无人值守生产发布。

### 阶段 B：策略、验证与 ACP Task 接入完善

增加深入预设、影响范围驱动检查、真实运行/浏览器检查、保守证据复用、重复失败识别、mfcli Task 兼容和能力提示、预算与速度指标、按需委派和隔离。

验收：简单描述的复杂故障可以加强策略，反之不硬跑流程；检查失效正确；mfcli 与 Pi 统一显示标准但不伪装能力；模型/提供商不会未经策略切换。

### 阶段 C：实际交付

增加可追溯提交/推送、项目发布配置、操作记录与状态对账、发布后检查、授权回滚；Automation/Todo 接入同一 Task 完成语义。

验收：指定项目从任务到测试环境发布闭环跑通；发布响应丢失不盲目重复；发布产物与验收产物一致；失败可见、不可逆迁移不随意回滚。

### 阶段 D：由使用数据决定

独立后台 Host 生命周期、多任务资源调度优化、真正需要的并行协作、Pi 执行核心/传输分离。只有阶段数据证明值得，才展开这些工程，不把移除 ACP 写成必达里程碑。

## 19. 验证矩阵与指标

### 19.1 功能与故障场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 小文案修改 | 无固定额外模型轮次，最小必要检查，正确 diff |
| 类型检查通过但原始 Bug 仍存在 | 不成功，继续具体复现/修复 |
| Pi 自述通过但没有记录 | 显示上报/未核实，不伪造证据 |
| Pi 内部重试/压缩 | 不重复派发同一需求，不提前完成 |
| Host 崩溃后重启 | 先采用旧执行或对账，再恢复，无双执行 |
| 提交回执丢失 | 相同 commandId 去重，对外副作用查询实际状态 |
| 执行中取消、取消与成功竞态 | 状态符合持久化意图，不复活、不遗留假绿灯 |
| 关闭 Task 页面/普通 Session | Task detach 与原 Session close 各自语义正确 |
| 同目录第二个托管写入任务 | 正确排队；父子任务不死锁 |
| 外部修改、切分支、改测试配置 | 受影响证据失效，交付边界重新核对 |
| mfcli 缺少深度事件 | 能力限制透明，必要检查由 Host 补足或阻塞 |
| 提交/部署时未知状态 | 不宣布成功、不盲目再次发布 |
| 预算耗尽 | 保留已有结果和未完成项，不降低标准 |

从状态机单测、fake Driver、临时仓库集成到真实 Pi/mfcli 和 Desktop 路径逐层验证。先做确定性故障注入，再在明确测试环境运行真实模型/发布；不能把 mock 测试通过当作真实交付验证。

### 19.2 衡量速度与标准

记录分任务类别的真实交付耗时、一次交付通过率、人工接力次数、错误完成率、模型请求数、输入 token、原生重试与修复次数，以及队列/启动/上下文/模型/工具/验证/发布的耗时。

小任务与现有直接 Pi 对照：固定额外分类/规划/评审/总结调用的目标是 0；必要业务工具交互不计为无意义开销。记录冷/热启动和相同项目、模型、输入，比较分位数，不将不同任务混在一起追求平均值。

第一版不承诺未经测量的提速倍数或具体秒数。取消也分别记录“接受请求耗时”“执行确认停止耗时”和“未确认资源”，不能拿 UI 变色冒充进程已停止。

质量指标用独立回归场景、实际验收和后续返工统计，不能由模型给自己打分。用户提前取消或外部阻塞与执行质量失败分开统计。

## 20. 第一版最重要的设计检查

一个小任务是否被迫填写表单、加载全仓、启动多个 Agent、重复测试或新建 worktree？有则删掉不必要开销。

一个复杂任务是否仍然需要用户不断说继续、是否仅凭 idle/自述通过、是否验证了过期代码？有则尚未形成可靠闭环。

实现是否因为兼容 ACP 限制 Pi，或者因优化 Pi 删除 mfcli？两种都不符合本方案。

最终判断：小任务保留直接用 Pi 的效率，复杂任务减少人工接力；完成时能说明做了什么、验证了什么、交付到哪里，以及哪些事情尚未确认。
