详细结论

1. Discussion 是 workspace 级实体

它拥有自己的 id、议题、参与者、轮次、状态和最终结果。发起对话只保存引用关系，因此关闭或切换主对话不会让讨论记录消失。右侧栏可以根据当前会话关联自动打开对应讨论。

2. 两位参与者必须严格平等

第一轮双方在看不到对方答案的情况下独立表达。后续每一轮都使用同一份已冻结的上下文快照，并行生成回应。界面不出现 reviewer、owner、approve 等暗示权力差异的词。

3. 长结果需要“摘要 → 细节 → 原文”的阅读层级

工具返回给发起 Agent 的内容可以完整，但右侧面板默认先显示执行摘要和关键决策。详细推理按主题分段，双方逐轮原文折叠在最后，避免用户为了找到结论滚过大量重复论述。

4. 用户补充应在轮次边界生效

用户输入不会只发给正在输出的一方，而是进入共享 pending guidance。当前轮完成后，Host 将同一条补充同时加入双方下一轮输入，从而维持语义公平和可复现性。

5. 返回发起 Agent 的结果应结构化

结果至少包含共同结论、双方最终立场、未解决分歧和完整 transcript 引用。发起 Agent 可以直接用摘要回答，也可以在需要时读取具体轮次，不必把全部原文再次塞入自己的上下文。

CClaude · 最终立场742 字 · 第 3 轮

我认为这个能力的产品边界应当由“一个共享讨论对象”决定，而不是由参与者会话决定。用户需要稳定地看到议题如何演进：独立立场、交叉回应、共同结论，以及仍未解决的分歧。

在运行层面，隐藏 participant session 是合理实现，但不应泄露成两个普通聊天标签。每轮必须保存输入快照和贡献引用，使 Desktop 重启后能够恢复到明确阶段。对于用户补充，我更重视纠偏速度，因此建议允许用户选择立即取消当前轮。

最终返回发起 Agent 时，应提供简短综合结论以及可按需展开的原文引用，避免把几千字讨论直接复制到主会话。

OCodex · 最终立场816 字 · 第 3 轮

我同意共享 Discussion 是正确的产品模型，同时强调它应由确定性状态机驱动。双方在每一轮读取完全相同的共享快照，分别写入贡献，Host 只在两份贡献都终止后推进轮次。

长讨论结果不能只依赖一个总结字段。建议存储结构化 summary、agreements、disagreements 和 participant conclusions，同时把完整 contribution 作为按需读取的历史。这样主 Agent 接收的是可控大小的结果，而右侧栏仍可浏览完整推理。

用户补充默认进入下一轮是最安全的。如果需要立即纠偏，应明确取消双方当前输出并从同一个新快照重新开始，而不是只 steer 其中一方。
