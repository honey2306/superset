# Task 的核心、工具、记忆与技能边界

更新：2026-09-19。扩展边界已开始落到代码：技能管理复用现有入口，检查执行与 Git 交付通过窄接口接入核心；不是对全部运行时的一次性重写。
总体方案见 `plans/20260919-task-runtime-pi-first-design.md`；已实现行为见 `TASK_RUNTIME.md`。

## 1. 产品原则

以最短的合理路径，交付达到约定标准的结果。Task 是工作容器，不是所有任务必须走完的流水线。
接下来优先复用现有工具、记忆和技能，不再按“分析、规划、浏览器验证、提交、部署、复盘”逐个给核心增加必经阶段。

Pi 负责问题求解与工具选择；核心负责这次工作是否仍在推进、能否停止、是否有真实证据、是否允许完成。
技能改变“如何做”，不能改变任务状态、验收标准或当前授权。记忆提供知识，不能成为外部副作用的批准凭据。

## 2. 四类内容放在哪里

| 类型 | 负责内容 | 例子 | 不承担什么 |
| --- | --- | --- | --- |
| 核心控制 | 目标/要求版本、运行所有权、停止恢复、预算、证据有效性、完成/阻塞状态 | 取消后不复活、旧要求不能完成新任务 | 项目测试做法、部署平台步骤、全量项目知识 |
| 执行能力/工具 | 实际文件/进程/浏览器/Git 等操作与可查询结果 | 运行检查、返回退出码、对账提交/推送 | 决定产品目标、凭字符串宣称验收通过 |
| 项目记忆 | 有来源、适用范围和更新时间的事实、决策、经验 | 服务入口、特定故障根因、常见环境问题 | 活动 Task 状态、最新凭据、永久发布授权 |
| 技能 | 可复用的方法、判断步骤和按需引用的资料/脚本 | 复现流式 Bug、验证浏览器交互、某项目测试环境发布方法 | 另一个 Agent Loop、强制流水线、执行凭据或验收权威 |

“标准”不等于固定步骤。选哪些复现/观察可以由技能辅助；实际检查记录、输入版本和 required 条件是否满足必须保留可信状态。
“速度”不等于省验证。只加载相关索引/技能和必要检查，不每次请分类模型、额外评审模型或完整初始化环境。

### Project Profile 不是第二套记忆系统

Profile 中保留确定性的执行契约：已批准检查的 ID/命令/适用范围、超时、验收模式和版本。
项目架构长文、发布教程、错误排查故事不继续塞入其 `instructions`，优先放现有记忆或技能引用。

同一个事实不要同时抄进记忆、Profile、SKILL.md 三处成为三个权威。
例如技能解释怎样选择检查，实际命令以当前项目脚本或 Profile 为准；记忆可描述历史环境问题，但执行前要确认仍适用。
从记忆/技能发现的命令可以作为诊断建议，不能自动改写用户已批准的验收契约。现有数据不自动搬家或删除。

## 3. 当前源码已经具备的能力

`global-skills/global-skill-store.ts` 管理标准 `SKILL.md`，默认目录是 `~/.agents/skills`，现有 Skills 页面可编辑。
Pi 适配使用 `DefaultResourceLoader`；本地 SDK 0.84.2 的 package-manager 会发现受信任项目中 cwd 到 Git 根的 `.agents/skills`，
也会发现 `~/.agents/skills`。其系统上下文先提供名称、描述、位置，完整正文由 Agent 按需读取。项目信任和禁用规则仍生效。

非默认 `SUPERSET_GLOBAL_SKILLS_DIR` 现在由资源层显式传给 Pi 原生 additionalSkillPaths，不在 Task Runner 增加技能加载逻辑。
模型侧 `list_global_skills` 已改为仅返回名称、描述和位置，`get_global_skill` 按需读取一个技能正文；Pi 主路径继续使用原生元数据索引。
界面复用 `/skills`，增加项目/全局范围和完整技能包复制，详情与参考文件按需读取。保存不热更新活动会话，也不绕过项目信任。

无需再写 Task 专用 SkillRegistry、另一个 Prompt 路由模型或 SDK 内置能力的复制品。
SDK 元数据中存在技能不保证模型一定选择它；显式需要时可以要求读取对应技能。不能把新建文件等同于已在活动会话加载。

现有项目记忆有 project/global 作用域、来源、更新时间、标题索引和按需搜索工具。
继续遵守用户明确要求保存才保存的行为，不因完成 Task 就自动写入大量猜测或触发“复盘 Agent”。

ACP 继续兼容 mfcli。不同 Agent 的技能发现能力以实际支持为准，不假设都和 Pi 一样。
必要时在其支持的文件工具中显式读取相关 SKILL.md；不能为了统一接入，再新建一套强制所有引擎加载全部正文的机制。

## 4. 最初的技能提取（已保留）

新增 `.agents/skills/verify-behavior-change/SKILL.md`：处理行为 Bug 和功能变更的最小充分验证方法。
它只在复现/运行边界需要时使用，不匹配单纯文案修改。说明如何查相关记忆、选择复现、区分检查依据、处理新要求和报告缺口。
`references/superset.md` 单独保存 Superset 的包命令和验证边界，主技能不硬编码此项目的服务端口、机器路径或凭据。

这是本仓库的项目技能，**不是已经安装到用户所有项目的全局技能**。只有验证方法确实适合跨项目共享时，
再通过现有全局技能目录/页面显式安装整个技能包。引用了 references 的技能迁移时必须一起带上引用文件；
现在可用技能 UI 显式复制整个包；仅粘贴正文仍不会自动复制参考文件。参考和脚本在 UI 只读预览，使用外部编辑器修改。不要把私有项目细节默认写入全局技能。

最初的技能提取批次没有修改 Runtime/Driver/验收/Git 执行逻辑，没有增加 Task 状态、数据库表、模型调用、自动部署或全局配置写入。
新增测试验证本地 Pi 的实际发现/按需索引行为和技能格式，而不是构造另一个技能加载器。

## 5. 后续功能的处理方式

### 5.1 浏览器验证、原始复现、复杂排查

先写技能说明怎样识别目标实例、执行原始交互、观察状态和检查退化；使用已有 Browser/进程工具。
验证过程需要的新观察项保存为证据，不能因为放在技能中就只给一句“我测过了”。
只有确实缺少截图/进程/工件的执行接口时，才增加窄工具，而不是给 Runner 新增一个“浏览器 Agent 阶段”。

### 5.2 部署和发布

暂停此前“接着向 Task Runner 加一套通用部署引擎”的扩展路线。
先为一个真实项目提炼 `deploy-staging` 技能：适用项目、输入产物、现有脚本/CI 入口、结果查询、健康检查、失败处理边界。
脚本和 API 复用项目已有能力，信息缺失时不凭模板编造发布目标、凭据和回滚策略。

当前 Task 没有部署授权/执行端口，因此编写技能**不等于**已经支持部署，也不能让技能用任意 Shell 绕过现有交付限制。
将来确有自动部署需求，再增加最小的可取消/可对账发布能力接口。环境/平台差异放技能、项目配置和执行器，
核心只接收可验证的操作状态，不认识 Docker、Kubernetes、SSH、CI 厂商等逐个平台步骤。
外部副作用回执未知仍然需要真实查询；这部分不能只写在技能中交给模型猜。

### 5.3 Git 与验证

现有 `delivery/git-delivery.ts`、进程检查和文件归属代码保留，属于可选执行能力，不迁成 Markdown 后删掉保证。
Git 的“怎样处理某项目发布习惯”可放技能，index 保全、禁止误推他人改动、操作对账仍由代码执行。
已抽取 TaskVerificationCapability 和 TaskDeliveryCapability，实际执行由 ProjectTaskVerification、GitTaskDelivery 实现，task-composition 组装。Runner 保留取消、版本、证据失效和完成判断，不因为只有两个能力就先搭插件市场、总线或通用 DAG。

### 5.4 评审、多 Agent 与长期知识

独立评审和委派是按需方法，不是每个任务的强制环节。需要新增工具时遵守当前执行所有权/共享目录约束。
有用经验经用户要求沉淀为项目记忆；重复出现且可清楚描述的方法才提炼技能。
任务的实时进度、检查和提交记录继续留在 Task/Run 数据中，不当成模糊的长期记忆取回。

## 6. 一个具体运行例子

用户：“修复流式文本被后续工具事件截断，验证相关场景。”

Pi 从项目记忆按需获取已知消息链路和历史坑；当确实需要运行复现时读取 verify-behavior-change。
技能引导检查原始事件序列、复现和必要回归；Pi 调用现有工具修改/诊断，Host 执行当前批准检查并记录结果。
无需 Runner 硬编码“这是流式 Bug”、无需无关部署步骤，也不因为存在该技能就给按钮文案任务增加相同流程。

如果发现需要新增项目检查，提出缺口或请求批准；技能不能自行把原检查替换成一个总是返回 0 的脚本并把任务标绿。

## 7. 每次加功能前的准入判断

1. 是项目事实或历史经验吗？放现有记忆，标明来源与适用范围。
2. 是可以用已有工具完成的做法吗？先提炼技能/参考资料，不改 Runner。
3. 是缺少一项真实执行与观察能力吗？增加小工具或能力模块，返回真实结果。
4. 是所有 Task 都需要的生命周期或可信性不变量吗？才考虑进入核心。

可选技能不成为默认关键路径，不要求额外模型分类，不自动加载全文，不自动改变授权。
没有技能时，原有 Task 仍可工作；没有核心控制与真实证据时，技能不能让任务变得可靠。

## 9. 技能 UI 与能力边界已实施

复用 MCP/记忆旁边的 Skills 页面，加入项目/全局范围、按需详情、编辑预览、完整包复制、重命名保留附带文件、版本冲突和未保存草稿保护。
不新增技能数据库、不安装用户全局技能、不迁移记忆、不创建强制技能选择阶段。项目 `.agents/skills` 与原生 Pi 默认资源规则继续兼容。

任务执行器经窄能力接口组装，核心不再构造 Git 实现或逐命令执行项目检查。真实进程、输入版本、取消/恢复与 Git 对账代码仍然保留，未改成让模型凭 Markdown 自述保证。
项目 Profile 的必要约束保留；提示上下文里的项目检查改为 ID/名称索引，命令和适用路径需要时通过已有 get_task 获取。没有把每个任务额外加一次 get_task 作为仪式。

实际使用、限制、测试复现见 `SKILLS.md`。本批不以“纯核心”名义重写所有持久化类型，也不扩展自动部署、多 Agent 和后台服务。

## 10. Task 回归正常聊天与有限目标续跑

Task 的主要交互回到已接入 ACP Agent 的正常聊天：同一输入框选择任务模式、同一 Session 和模型执行、内联进度/检查、结束后回到普通对话；独立页面只作为总览和高级入口。
早停续跑和要求覆盖检查是已有任务完成边界的补全，不是新增一套规划/评审模型。缺少报告有有限恢复次数，明确未完成可继续，已知验证缺口保持待验收。详细方法依旧由 Pi 和按需 Skill 决定。
结构化“要求→检查”映射仍可能由模型判断错误，因此不能声称已经自动证明所有自然语言目标。已运行事实与模型自述在 UI 分开呈现。实现与限制见 TASK_CONVERSATION.md。


## 11. ACP Agent 示例不应变成任务产品边界（2026-09-19）

Task 已改为复用现有 ACP_AGENT_HARNESS_BY_AGENT_ID，而非维护 Pi/mfcli 两项白名单。
当前目录中的 Claude、Codex、Pi、MyFlicker、DeepSeek 使用相同的任务准入、状态、验收和聊天 UI；
登录、模型、工具和是否支持实时指导仍由实际执行引擎决定。无法提供完成依据就报告缺口，不伪造功能对称。
自动 Git 交付所需 Pi 原生修改归属保持独立限制，不因为放开普通执行就放开不可靠的发布。

任务页空白是 flex row 下内容根节点未伸展的布局 bug，修复后占满父容器；无数据和筛选无结果不再预留详情栏。
聊天选择器收入原输入框，任务状态条紧凑展示、要求和检查按需展开，没有新增输入区或模型步骤。
